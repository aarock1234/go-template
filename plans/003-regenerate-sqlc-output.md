## Why this matters

The `go:generate` directive pins sqlc `v1.31.1`, but the four committed
generated files are stamped `v1.30.0`. A user's first `make generate` in a
fresh project therefore rewrites headers in files unrelated to their change.
The sqlc config also carries an option that has no effect with the pgx
driver, an initialism left over from another project, and six type overrides
that import a module the project does not require — without a word to tell
the user that their first nullable column needs `go mod tidy`. After this
plan, regenerating in a fresh project is a no-op and the config explains its
one surprise.

## Maintenance notes

- CI does not check that generated code is current, which is how the header
  drifted. A CI step that runs `make generate` and fails on a dirty tree
  would prevent a repeat, at the cost of compiling sqlc on every run. That
  trade-off is left to the maintainer.
- When the sqlc pin in `pkg/db/db.go:4` is bumped, regenerate in the same
  commit.
- The overrides remain unexercised until a schema with a nullable column
  exists.
